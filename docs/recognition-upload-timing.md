# 认可提交耗时诊断

本地候选版本2026.10.25.1新增诊断；部署后才会在生产生效。当前单条和多条登记仍等待照片接收、校验及事务提交成功，不新增上传状态、不改变复核或计分。

`POST /api/recognitions` 与 `/api/recognitions/batch` 每次请求通过 `uvicorn.error.recognition_timing` 输出一行 `recognition_request_timing` JSON，使用既有Uvicorn日志配置。响应带 `X-Recognition-Request-ID`；服务端生成独立标识，不采信客户端提供的标识。可按UTC起始时间、操作人内部ID与标识关联请求；北京时间为UTC加8小时。

| 字段 | 含义 |
|---|---|
| `request_id` / `started_at_utc` / `operator_id` | 请求关联标识、服务端收到请求的起始时间、业务入口核实后的操作人内部ID |
| `status` / `error_type` / `disconnected` | 响应状态、未处理异常的类型、已观测到的连接中断；不记录异常文本 |
| `received_bytes` | ASGI实际收到的请求体字节数，包含表单封装，非单独图片大小 |
| `receive_wait_ms` | 等待ASGI接收请求体的累计时间，包含网络、代理及服务器调度影响，不能当作纯网络上传时间 |
| `body_complete_ms` | 从服务端请求开始到读取完整请求体的时间；未读完为null |
| `response_start_ms` / `total_ms` | 到开始响应、应用完成响应处理的时间；不代表浏览器收完响应的时间 |
| `after_body_ms` | 请求体读完到开始响应的时间差，用于区分体接收与其后处理 |
| `stages_ms.image_write_ms` | 图片流写入暂存文件及哈希计算 |
| `stages_ms.image_validate_ms` | 图片格式/解码校验及等候解码线程，包括排队 |
| `stages_ms.write_lock_ms` | 多条登记申请SQLite写保留锁的等待和执行时间 |
| `stages_ms.record_ms` | 业务记录处理，单条包含图片阶段，多条逐条累加；与其他阶段可能嵌套，不可直接相加 |
| `stages_ms.commit_ms` | SQLite最终事务提交时间 |

未执行的阶段不输出。失败请求也保留已测阶段，原异常和响应继续按现有方式处理。日志不包含表单内容、姓名、照片、文件名、密码、令牌、请求头、查询参数或幂等键。后台图片哈希扫描、表单解析等未单列的工作可体现在总耗时中，不能把剩余时间全部归因于网络。

## 后台上传讨论（尚未实现）

用户期望：提交后首页展示“图片上传中”，成功后才进入“待复核”；失败提示并提供再次上传。此方案缩短页面阻塞等待，不会缩短相同图片本身的传输时间。

建议后续实现时，将上传任务与可复核业务记录分开：保留待上传表单及任务标识，校验图片成功后原子生成独立的待复核记录。失败、刷新、断网重试沿用同一任务标识，服务端核实最终结果，防止重复登记；上传中和失败任务不进复核队列、不计分。多条登记共用图片仍须保持整批成功或失败以及逐条审核。

页面切换与浏览器关闭是不同情况：可在工作台页面切换后继续上传，但手机锁屏、关闭网页或系统终止浏览器不能承诺继续。需设计照片/表单的本地持久化、账号隔离、退出清理、恢复与重选照片流程；服务器应保存明确状态。未确定这些细节前，不以简单前端异步请求替代可靠上传任务。
