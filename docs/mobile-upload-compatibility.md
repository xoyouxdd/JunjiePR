# 手机浏览器认可图片上传兼容

本地候选：2026.10.20.4。覆盖单条认可和CM/TR本人批量认可，共用读取、图片封装与错误处理，不根据浏览器品牌开放或拒绝业务权限。

## 目标范围与实现

目标包括iPhone Safari、UC、百度浏览器/百度App、微信内置浏览器，以及安卓Chrome、UC、百度、QQ、华为等主流浏览器。浏览器名称只用于失败审计分类，不参与上传放行条件。

上传链路分为选取、读取、加入multipart和服务器接收；显示文件名不作为上传成功证据。

- 使用标准文件列表、FileList.item与原生表单文件读取；当前页面内保留有效的已选文件，清空、重新选择与成功提交后作废。
- 单条和批量统一用appendRecognitionImage加入image文件字段，避免批量和单条采用不同的文件装入方式。
- 发送前检查multipart中有且仅有一个真正的文件对象，名称与大小正确，禁止路径文字或空文件代替图片。
- 原File包装对象被序列化成文字或无法装入时，以原字节Blob切片重建；显式保留原文件名。不转码、不重新压缩，不去除原图内容。
- 两条路径仍失败就不发送请求；保留已填写内容。只有文件字段检查成功后才添加image_client_ready，不能仅靠此标记宣称后端收到图片。
- 后端明确返回缺图时，按原提交快照、原幂等键强制用Blob重新封装，只重试一次。兼容批量的422图片字段校验与旧单条入口的专用400缺图文本；接口返回不变。其他400、权限、计分冲突、其他字段错误与网络结果未知均不自动重试；持续缺图最多两次请求。
- 服务器继续原有图片签名、解码、格式、大小与像素检查；沿用权限、原子事务、计分、复核、审计和幂等规则。

## 自动化验证

recognition_upload_ui.cjs导入真实业务模块，使用真实File/FormData和HTTP接收端解析multipart，对接收端文件逐字节核对。覆盖：

1. 正常文件、仅item可访问、原生表单后备、选取后文件桥接失效。
2. File装入被转成文字、装入File抛异常、文件set失效。
3. 中文文件名、单条和两条共用照片。
4. 后端明确缺图后的恢复、重试上限和未知结果不重试；重传使用同一快照，期间修改表单不改变原提交。
5. 无法恢复的文件在发送前拒绝，不遗留虚假的就绪标记。

2026-10-20在Windows上的Edge、Playwright WebKit和Firefox引擎运行：81项场景通过，HTTP接收端实际收到54次完整文件，其中6次在先收到明确缺图错误后恢复；另有发送前拦截、普通错误不重试与缺图重试上限检查。它们证明这些引擎和模拟故障的处理，不是54次真实手机提交。

后端还验证缺图返回不创建认可记录或图片、不改变原记录并列序列；之后同幂等键补图成功，重复请求仍只有一条记录。

另以合成浏览器标记测试百度、UC、微信、QQ、Chrome与Safari的真实后端单条/批量入口：文件保留原字节、原名称、原待复核状态。浏览器标记测试不能证明相应品牌手机客户端已认证。

完整前端模块可通过FRONTEND_TEST_ENGINE=edge、webkit或firefox选择引擎；正式默认验证使用现有Edge环境。

```powershell
$env:UPLOAD_TEST_ENGINES='edge,webkit,firefox'
node backend/tests/recognition_upload_ui.cjs
$env:FRONTEND_TEST_ENGINE='webkit'
node backend/tests/frontend_modules.cjs
```

额外引擎须安装与项目Playwright匹配的浏览器。未安装时明确失败，不把缺少引擎当作已通过。默认完整run_all.py已纳入Edge上传接收端回归。

## 真机验收

尚需实际iPhone/安卓设备上验证相册权限、拍照、选图后返回前台、取消和重选、同名不同照片、大图及HEIC。WebKit引擎测试不等同于iOS Safari或UC/百度的App封装测试；部分App的隐私设置、云端模式和系统权限需要在对应设备实测。

本轮无生产写入、推送或部署。既有UC事件的服务器只读核对和根因边界见[UC复查记录](uc-upload-review-20261020.md)。

兼容复查另修复WebKit点击“关于系统”后关闭弹窗时未回到触发按钮的焦点问题；手机从更多菜单打开时回到“更多”。未改变导航权限。
