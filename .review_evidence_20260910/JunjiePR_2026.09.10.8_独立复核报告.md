## 3. R4-S01：依赖只修了 multipart，尚未排除文件响应的已知问题

**优先级：P1。类别：受影响依赖声明和相关调用点已确认；生产实际安装与可利用性待验证。**

位置：`backend/requirements.txt`；`backend/app/main.py` 的 `StaticFiles` 挂载；使用 `FileResponse` 的文件接口。

当前固定 `fastapi==0.116.2`、`starlette==0.47.3`。Starlette 官方公告 `GHSA-7f5h-v6xp-fcq8` / `CVE-2025-62727` 的受影响范围为 `>=0.39.0, <=0.49.0`，该问题在多 Range 文件响应处理时可能导致 CPU 资源耗尽，修复点为 `0.49.1`。应用公开挂载 `/static`，不是完全没有使用相关组件的无关依赖。

本轮没有向生产发送利用请求，也未确认外层代理是否已有缓解。现有声明命中公告的事实，足以要求发布前处理。

**最小修复：** 升级经过兼容解析和测试的 FastAPI/Starlette 组合。FastAPI 0.116.2 官方约束是 `starlette>=0.40.0,<0.49.0`，因此不能仅把 Starlette 硬改为 0.49.1 后使用 `--no-deps` 绕过冲突。0.49.1 只是这份特定公告的修复点，不代表截至今天所有安全问题都已消失；应扫描实际解析安装后的完整依赖树。

**验收：** 保存完整依赖清单、依赖一致性检查、当前公告扫描结果；正常静态文件、图片/PDF、单 Range、条件缓存请求正常；隔离环境验证恶意复杂 Range 被安全拒绝或有界处理。验证 CM/TR 的真实图片保存路径及 100MB 边界，不只验证管理员代录接收一个大于 1MB 的文件。

**副作用与回滚：** 关注 PDF/文件响应、上传解析、异常格式和 Windows 原生依赖。锁定一组组合，而不是独立更换底层库；若新版不兼容，应回到隔离环境修复，不将已知受影响组合自动重新对外开放。

## 4. R4-M01：失败处理仍会先删除源文件，随后提交失败可使材料线程退出

**优先级：P1。类别：已确认实现缺陷，已做隔离故障注入。影响所有材料提交角色，电脑/手机均可触发对应业务路径。**

位置：`backend/app/deduction_materials.py` 的 `_discard_failed_sources()`、`process_next_deduction_material_job()` 和 `start_deduction_material_worker()`。

成功路径已经改好，但 `except MaterialError` 路径仍为：

```text
转换失败 -> rollback -> 设为失败 -> 删除源文件 -> 写审计 -> commit
```

本轮向最后一次“保存失败状态”的 commit 注入提交前异常，得到：

```text
源文件：不存在
任务数据库状态：processing
业务状态：material_processing
失败审计：0 条
OperationalError：逸出 process_next_deduction_material_job
```

在此 except 分支内再次抛出的异常，不会被旁边的 `except Exception` 捕获。当前 worker 循环也没有最外层异常保护，因而这类异常可结束材料线程。该结论不是称生产已经发生事故，而是代码及指定故障场景的可复现结果。

另外，普通异常分支现在仅 `rollback(); return True`，没有错误记录、重试上限或可见告警；成功后清理失败也没有持久化清理待办。不要把函数返回 True 解释为“业务成功”。

**最小修复：** 成功和失败路径均先可靠持久化状态，再执行独立、幂等、可重试的源文件清理。新增清理待办/可恢复标记或等价机制。给 worker 循环增加异常记录与存活保护，明确错误分类、退避、尝试上限、人工处理入口。提交结果未知时先查询持久化状态核对，不能直接重新执行整个业务。

**验收：** 同时注入转换失败、失败状态提交失败、成功提交前失败、成功后清理失败、进程终止。不得出现“数据库说正在处理但唯一源材料已丢”；后续正常任务必须仍可处理。明确区分提交前失败与提交结果未知测试。

**副作用与回滚：** 延迟清理增加短期磁盘占用，需要留存/容量上限。不能用无限保留替代恢复设计，也不能为了回滚覆盖已经产生的新业务数据。

## 5. R4-M02：任务可超时接管，但旧执行者仍能发布结果

**优先级：P2，当前单进程运维约束下为条件性风险；启用多实例前必须解决。类别：已确认控制缺口，隔离时序实验复现。**

位置：同一材料模块，`claim_next_deduction_material_job()` 仅返回 job_id；15 分钟 stale 接管后，最终提交没有校验领取代次/所有者。

实验不是等待真实 16 分钟，而是在独立环境控制领取时间：

```text
A 领取并停在转换阶段
B 在模拟 16 分钟后接管并成功，数据库指向 worker_B.pdf
A 恢复并完成，数据库又被改为 worker_A_late.pdf
结果：完成审计 2 条，两个生成文件均留在磁盘
```

这证明“普通同时领取只有一个成功”不等于“超时接管全生命周期安全”。实验没有证明分数被重复相加，不应把重复完成审计写成重复计分事故。

**最小修复：** 领取时返回并保存唯一 token/单调代次，续租、成功和失败提交都校验当前所有权；丢失所有权的执行者只能放弃自己的临时产物，不能改业务状态、删共享源文件或覆盖新结果。转换可能很长时补心跳/续租。不要只做“提交前 SELECT 检查”而留下检查到提交之间的竞争窗口。

**验收：** A 暂停、B 接管成功、A 再恢复，最终仍只有 B 的有效结果；A 延迟失败也不能把 B 已成功记录改成 failed。多线程普通 claim 测试继续保留。

**副作用与回滚：** 若新增列/索引，使用新增迁移身份，旧任务明确回填。当前 docs 已建议继续单进程，这是有效的缓解，应保持，不能把此次 claim 修复理解为允许直接扩容多个 worker。

## 7. R4-U02：取消发生在读取 JSON 阶段时，被吞成空对象，旧页面仍可写入

**优先级：P2。类别：已确认代码路径，受控 Response 流实验复现；真实网络端到端未验。角色：所有可切换模块的用户。**

位置：`app.js` 的 `api()`、`renderChangelog()`，以及 `render()`/各页面函数的写入边界。

问题代码：

```javascript
const body = await res.json().catch(() => ({}));
```

`fetch()` 的异常保护不等于 `res.json()` 的异常保护。代码把读取正文时的取消错误、解析失败等都转成 `{}`，随后旧页面可以正常完成并写入公共容器。

本轮使用浏览器原生 Response 和受控 ReadableStream 注入 AbortError：

```text
取消前设置的新页面：当前新页面B
旧函数完成后：更新记录 / 当前系统 V（空） / 暂无更新记录
旧函数结果：resolved，而不是 AbortError
```

这里不是用真实网络跑通了整站切页；本地 HTTP 尝试被浏览器策略阻止后，改用无网络的受控流进行函数验证。该实验明确反证“取消异常一定会一直向上传递”。

**最小修复：** 正文读取阶段同样透传取消错误；约定应返回 JSON 的成功 API 遇到无效 JSON 应报协议错误，不返回假成功空对象；真正允许无正文的响应明确处理。页面提交 DOM 前检查本页请求上下文/代次。对同一页面的月份、筛选、历史切换也增加独立过期结果保护。

**验收：** 慢网下在响应头前、头后正文前、正文解析中分别切页；最后一次页面选择始终有效。无效 JSON 不产生“空列表成功”。已成功业务提交但响应未知的情况仍需回执核对，禁止盲目重试。

## 9. SQLite、预检、文档和证据补充

### 索引不建议机械重排

本轮新增测试确实调用了 `PRAGMA index_xinfo` 和 `EXPLAIN QUERY PLAN`。这是进步。但它主要在小型新库插入一条认可记录，并验证索引名、列顺序及没有某种全表扫描文本，不证明 10 倍/50 倍数据量性能，也不是两组索引顺序的 A/B 对照。

当前以圈开头的月结索引服务单圈查询；全局查询可选其他月份索引，是否需要改成月份开头，应在真实结构和统计信息下比较。不能因缺少左侧圈条件就绝对断言 SQLite 不可能使用该索引，也不能把任何 SCAN 均认定为坏计划。**在获得代表性结果前，保留现有索引，不为了消除一条审查建议随意改顺序。**

### 分值预检是工具，不是生产核验回执

`audit_score_rules.py` 不自动删除分值，这是正确的。`matches_seed_default` 只表示数值与默认值相似，不证明该行错误；当前输出不含规则主键和修改审计匹配，应补 rule_id 及相关审计信息，供人工确认。

脚本使用常规 SessionLocal，没有显式 SQLite `mode=ro`。它不执行业务写语句，但建议把“不会改业务记录”和“底层数据库只读连接”分开：要求明确指定一个已存在的隔离快照，用只读连接，避免误路径新建库或执行写型初始化 PRAGMA。未对生产运行该脚本，也没有依据声明历史异常规则已经清理。

### 测试和文档不能替代运行证据

材料新增测试覆盖普通竞争领取与 stale 再领取，尚不覆盖旧执行者恢复、失败分支提交异常及成功后清理中断。部分 UI 测试仍只是查源码中有没有字符串。

大文件测试使用约大于 1MB 的随机图片，且走管理代录；它有助于检测 multipart 基础兼容，但不等于覆盖 CM/TR 留证保存、100MB 临界、并发延迟与恢复。

`.7` 更新记录中的“大文件不再卡死服务”、`.8` 的“一次只能被一个人领取”等表达应缩小为明确已验证范围，避免把某一个修复等同所有负载/恢复场景已保证。完整备份恢复仍需实际运行记录，不能用文档新增一个段落视为演练完成。

## 10. 本次独立实验清单

| 实验 | 结果 | 限制 |
|---|---|---|
| 两线程普通 claim | 1 成功 + 1 None；attempts=1 | 必要字段的独立 SQLite 模型，非原应用全栈 |
| 成功提交前异常 | 源文件保留，任务 processing，生成文件暂留 | 注入提交前故障，未测真实提交失确认 |
| 失败状态提交前异常 | 源文件已删除、状态 processing、异常逸出 | 受控转换失败 + 提交故障 |
| A 超时、B 接管、A 恢复 | A 覆盖 B 输出；两条完成审计 | 模拟时钟；转换器为测试替身 |
| 复核确认后的分值显示 | 六个视口均未同步计入分和原因 | 当前原函数 + 合成 API/样式/辅助函数 |
| JSON 读取取消 | 被吞为 {}，旧页面写入新容器 | 原生 Response + 受控流；非真实网络 |
| 原仓全部测试 | 未执行 | 完整仓库未本地拉取 |
| 完整应用六尺寸 / 真机 | 未执行 | 没有可运行原应用和真实设备 |

运行环境：Python 3.13.5，SQLite 3.46.1，SQLAlchemy 2.0.50，Chromium 144.0.7559.96。特别注意，本地 SQLAlchemy 不是项目固定的 2.0.36，必须在项目锁定环境再执行集成测试。不要把上述版本差异隐去。

实验中的“未通过”用于证明残余实现缺陷；不是故意让原仓测试失败。源码片段文件与完整原模块不同，片段哈希不得冒充 Git blob 哈希。

### 批次 A：依赖与故障恢复
